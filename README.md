# Импорт персонажей для Virtual TTG

Внешний модуль [Virtual TTG](https://github.com/TTG-Club/vttg): переносит
персонажа с листа [TTG Club](https://ttg.club) прямо в мир — вместе с классом,
видом, предысторией, владениями, чертами и инвентарём.

Работает с файлом, который отдаёт кнопка **«Экспорт»** на листе персонажа
(`.json`). Собранный актёр появляется в списке персонажей мира.

## Что импортируется

| С листа персонажа | Во что превращается | Примечание |
|---|---|---|
| имя, аватар | имя актёра, аватар **и картинка токена** | картинка скачивается с сайта в файлы мира (`avatars/`); если не вышло — остаётся ссылкой на сайт, о чём модуль скажет |
| `abilities` | `system.abilities` | как есть, без пересчёта |
| `characterClass` + `additionalClasses` | `system.classes` | ключ берётся из ссылки: `fighter-phb` → `fighter` |
| `health.levelGains` | `classes[].hitPointsGained` | модификатор Телосложения вычитается — система добавит его сама |
| `hitDice` | `classes[].hitDiceUsed` | сколько костей уже потрачено |
| `species`, `size` | `system.species` | происхождение (lineage) переносится только названием вида |
| `characterBackground` | `system.background` | вместе с повышениями характеристик и чертой происхождения |
| `skills`, `savingThrows`, `proficiencies` | `system.proficiencies` | навыки без владения не переносятся: для системы это одно и то же |
| `armorClass` | `system.armorClass` | КД считает система по надетому доспеху; ручной и природный КД переносятся как есть |
| `health`, `speed`, `vision` | хиты, передвижение, зрение токена | тёмное зрение уходит в настройки токена |
| `currency` | `system.currency` | медь/серебро/электрум/золото/платина |
| `classResources` | `system.classCounters` | владельцем счётчика становится основной класс |
| `features` | `actor.features` | разметка сайта (`{@glossary …}`) разворачивается в markdown |
| `inventory` | `actor.equipment` | оружие с формулой урона, доспех с КД и лимитом Ловкости, магические бонусы — активными эффектами предмета |
| `personality` | описание актёра | мировоззрение, возраст, внешность |
| `carryingCapacity` | `system.carryingCapacity` | размер, своё значение и прибавка; незнакомый размер не подменяется «средним» |
| `spellcasting.prepared` / `preparedCantrips` | `system.preparedSpells` / `preparedCantrips` | число-прибавка листа становится записью прибавки системы (`kind: flat`) |
| — | `token.disposition: friendly` | лист сайта — всегда персонаж игрока |

### Про картинку токена

Фишку на сцене рисует `token.imageUrl`, и на аватар актёра сцена не смотрит —
поэтому картинка кладётся в оба поля сразу. Но перенести её можно только если
она есть **в файле**: в экспорте это поле `avatarUrl`, и у персонажа без
загруженного портрета там `null`. Если на сайте портрет виден, а в листе
`"avatarUrl": null` — задайте аватар персонажу на сайте и экспортируйте лист
заново. Сводка в мастере импорта честно показывает, есть картинка в файле или
нет, ещё до создания актёра.

### Что НЕ переносится

Мастер импорта показывает это списком до создания актёра:

- **Заклинания.** Их механику (школа, время, компоненты, области) лист не
  описывает — добавьте заклинания персонажу из компендиума мира.
- **Истощение.** Это состояние, а не поле листа — наложите его на сцене.
- **Заметки листа.** Формат заметок на сайте свой.
- **Бонусы предметов, которых нет среди эффектов системы** — такие предметы
  перечислены в предупреждении поимённо.

## Установка

```bash
pnpm install
pnpm build
node scripts/installToWorld.mjs "D:/путь/к/папке/мира"
```

Модуль попадёт в `<папка мира>/modules/character-import/`. Дальше в мире:
настройки → «Управление модулями» → «Перезагрузить мир». В левом тулбаре сцены
появится кнопка импорта.

### Хэш-пин: почему модуль исчезает после пересборки

Приложение фиксирует хэш кода модуля при первом появлении
(`<данные установки>/installed-modules.json`) и дальше требует точного
совпадения — так ловится подмена файлов уже установленного модуля. Для
разработчика это значит, что **любая пересборка выглядит как подмена**: сервер
молча перестаёт отдавать манифест клиенту, и модуль пропадает из «Управления
модулями» вовсе. В логе мира это видно строкой:

```
[ModuleSettings] Модуль "character-import" не отдан клиенту: код не совпадает
с зафиксированным при установке
```

Снять пин из интерфейса нечем, поэтому это делает `installToWorld.mjs`: он
удаляет записи `<мир>:character-import` из реестра, и ближайшее чтение пиннит
новую сборку заново. Если приложение хранит данные в нестандартном месте,
путь можно подсказать: `VTTG_DATA_PATH="D:/.../Data" node scripts/installToWorld.mjs …`.

## Требования к хосту

| Что | Версия | Где объявлено |
|---|---|---|
| Приложение VTTG | не ниже **0.9.555** (проверено на 0.9.608) | `compatibility` в `module.json` |
| Система `dnd5e-2024` | проверено на **0.8.246** | `systemCompatibility` в `module.json` |

0.9.555 — первая версия, где в API модулей есть `api.actors` (разрешение
`actor-write`). В более старом приложении модуль не прячется молча: в
«Управлении модулями» его карточка приглушена и подписана причиной («Нужна
версия приложения не ниже…»). Нижней границы для системы не объявлено
намеренно: проверена только 0.8.246, а выдуманная граница отключала бы модуль
там, где он, возможно, работает.

Модуль пользуется:

- `api.actors.create` (с 0.9.566 хост проверяет черновик схемой Zod: непустое
  имя, `system` объектом, строки в `ownerIds`/`avatar`/`description`) — черновик
  модуля ей соответствует, системные корневые поля схема пропускает как есть;
- `api.assets.upload` — перенос картинки токена в файлы мира;
- `api.system.getActiveSystemId` — предупреждение, если мир не на `dnd5e-2024`.

Полный контракт — в `docs/MODULES.md` репозитория хоста. Права проверяет сервер:
создать персонажа может тот, у кого в мире есть право `CREATE_ACTORS` (у игроков
оно обычно есть), а правит актёра мастер или его владелец. Без права хост
отклоняет создание сразу, а не по таймауту. Настройки импорта (галочки мастера)
общие на мир и пишутся только от мастера — у игрока модуль их не сохраняет.

Модуль объявлен совместимым только с системой **`dnd5e-2024`**: форму актёра
задаёт она, и в мире на другой системе модуль отключён с понятной причиной.

### Повторный вход в мир

При выходе из мира хост снимает модуль целиком, а при входе исполняет
`client.js` **заново**. Поэтому в сборке не должно быть `const`/`let`/`class`
верхнего уровня — повторное исполнение классического скрипта упало бы на
повторном объявлении. Vite собирает модуль в IIFE (`(function(vue){…})(Vue)`),
так что всё объявленное живёт внутри функции; не меняйте формат сборки.

## Разработка

```bash
pnpm dev            # пересборка при изменениях
pnpm type-check     # проверка типов
pnpm test           # тесты парсера и конвертера
```

Сборка — IIFE (`dist/client.js` + `dist/styles.css`): хост грузит модуль обычным
`<script>`, а Vue берётся из `globalThis.Vue` хоста, чтобы компоненты работали на
том же экземпляре Vue, что и приложение.

Структура:

```
src/
├── main.ts               регистрация модуля, кнопка в тулбаре
├── types/vttg.ts         типы хостового API (копия контракта из docs/MODULES.md)
├── types/dnd5e.ts        целевая форма актёра системы dnd5e-2024
├── sheet/schema.ts       zod-схема листа персонажа
├── sheet/parse.ts        чтение файла и сводка
├── sheet/richText.ts     разметка сайта и узлы редактора → markdown
├── convert/              маппинг листа в актёра (классы, владения, черты, инвентарь)
├── import/runImport.ts   сценарий импорта целиком
└── ui/                   мастер импорта и кнопка тулбара
```

### Локальный лист для тестов конвертера

Тесты конвертера сверяют перенос с настоящим экспортом листа — дварфом-воином
1 уровня с магическим предметом и счётчиком ресурса. Это чужой лист, поэтому
в репозиторий он **не входит** (`fixtures/*.json` в `.gitignore`):

- есть файл `fixtures/dwarf-fighter.json` — проверки конвертера идут целиком;
- файла нет (чистый клон) — они пропускаются с пометкой `skipped`, а
  остальные тесты (разметка сайта, ключи, картинка, отказы хоста) идут как
  обычно. `pnpm test` и `pnpm type-check` зелёные в обоих случаях.

Лист читается во время выполнения (`src/testing/localSheet.ts`), а не
статическим `import` JSON: импорт отсутствующего файла ронял бы проверку типов.
Ожидаемые значения в тестах написаны под этот конкретный лист, поэтому
подкладывать на его место другой персонаж бессмысленно — тесты упадут.

## Тонкости формата

- **Ключи контента.** Лист опознаёт контент ссылками сайта (`dwarf-phb`,
  `item:greatsword-phb`), система — короткими ключами (`dwarf`, `greatsword`).
  Модуль снимает префикс типа и хвост источника; сам источник (`phb`, `dmg`)
  при этом не теряется — он остаётся в идентификаторе предмета.
- **Хиты за уровень.** Лист хранит ИТОГОВУЮ прибавку (вместе с модификатором
  Телосложения), система — «чистый» бросок. Модификатор вычитается при импорте,
  иначе после первого же пересчёта максимум хитов подскочил бы.
- **Урон оружия.** В формулу не попадает модификатор характеристики
  (`2к6`, а не `2к6+3`): систему он интересует отдельно, иначе бонус учёлся бы
  дважды. Кубики пишутся по-русски (`к`), как во всём контенте системы.
- **Магические бонусы.** Бонус предмета (`Сила 19` у рукавиц силы огра)
  становится активным эффектом предмета с `transfer: true` — он включается,
  когда предмет надет, и выключается, когда снят.
